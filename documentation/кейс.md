## Условие задачи

### Задание кратко

Вам необходимо с нуля развернуть в Kubernetes простое веб-приложение и
собрать вокруг него базовую инфраструктуру для публикации, мониторинга и
сбора логов.

В результате должно работать следующее:

- веб-приложение развернуто в Kubernetes;
- доступ к приложению организован через Kubernetes Gateway API;
- Prometheus собирает метрики развернутой инфраструктуры;
- Fluentd или Filebeat собирает логи приложения;
- решение должно поддерживать работу на Ubuntu 24.04;
- развертывание решения автоматизировано и может быть воспроизведено по
  вашей инструкции.

Итоговое решение должно быть полностью воспроизводимо на стороне
проверяющих экспертов на основании материалов Git-репозитория и не должно
требовать доступа к инфраструктуре участника или к специфическим
коммерческим сервисам.

По итогам онлайн-этапа необходимо предоставить:

- Git-репозиторий с конфигурациями, кодом автоматизации и инструкцией по
  развертыванию;
- краткий паспорт решения, позволяющий экспертам быстро понять архитектуру.

## Требования к обязательным частям решения

### 1. Kubernetes-окружение

Среду для разработки и тестирования участник выбирает самостоятельно.
Kubernetes-кластер может быть развернут локально, на виртуальной машине, в
собственной или облачной инфраструктуре. Предпочтительным решением
считается **kubeadm** от kubernetes.io (не привязанный к вендорам). Также
допускается использование kind, minikube, k3d и других совместимых
решений, но при прочих равных приоритет отдается решениям на kubeadm.

Итоговое решение должно быть полностью воспроизводимо экспертами на
основании материалов Git-репозитория и не должно требовать доступа к
инфраструктуре участника.

Для выполнения обязательной части задания решение не должно зависеть от
специфических коммерческих сервисов конкретного облачного провайдера.

Используемая версия Kubernetes должна быть указана в README.

Все дополнительные компоненты, необходимые для работы решения, должны быть
перечислены в README, а способ их установки — описан или автоматизирован.

В README необходимо указать:

- используемую версию Kubernetes;
- способ создания кластера;
- операционную систему, на которой тестировалось решение.

> Организаторы **не** предоставляют участникам Kubernetes-стенд для работы
> над решением.

### 2. Демонстрационное веб-приложение

Необходимо развернуть в Kubernetes простое веб-приложение. Допускается
использование любого простого open-source веб-приложения, например:

- Nginx;
- Angie;
- Apache HTTP Server;
- другое аналогичное open-source приложение.

Приложение должно:

- принимать HTTP-запросы;
- возвращать однозначно проверяемый ответ, например `Hello World!`;
- формировать access-логи HTTP-запросов, доступные для последующего сбора
  Fluentd или Filebeat.

Приложение должно позволить однозначно проверить успешность HTTP-запроса.

Используемый container image должен быть публично доступен либо участник
должен предоставить в Git-репозитории все необходимые материалы для его
сборки.

Разработка собственного приложения не является целью задания и не дает
дополнительных баллов.

### 3. Gateway API

Доступ к приложению необходимо организовать через Kubernetes Gateway API.

Минимально должны быть настроены:

- реализация Gateway API / Gateway Controller;
- `GatewayClass` (если он требуется выбранной реализацией);
- `Gateway`;
- `HTTPRoute`, направляющий HTTP-трафик к Kubernetes Service приложения;
- доступность приложения через настроенный Gateway API.

Участник самостоятельно выбирает open-source реализацию Gateway API.

В README необходимо указать:

- название реализации;
- её версию;
- используемые ресурсы Gateway API.

Участник должен предоставить способ проверки доступности приложения через
Gateway API, например команду `curl`, возвращающую ожидаемый ответ
приложения.

### 4. Мониторинг

Необходимо настроить мониторинг с использованием Prometheus. Prometheus
должен получать метрики как минимум от одного компонента развернутого
решения.

Вам необходимо:

- настроить сбор метрик;
- убедиться, что соответствующий target доступен Prometheus;
- продемонстрировать получение метрик с помощью Prometheus query;
- описать в README, какие метрики собираются и как эксперт может проверить
  их получение.

Сбор дополнительных метрик приложения и инфраструктуры является
дополнительным преимуществом.

### 5. Логирование

Необходимо настроить сбор логов демонстрационного приложения с
использованием Fluentd или Filebeat.

Вам необходимо:

- обеспечить сбор access/error-логов приложения;
- настроить их передачу в выбранное хранилище или точку назначения;
- продемонстрировать, что после обращения к приложению соответствующая
  запись появляется в собранных логах;
- описать в README, какие логи собираются, куда они поступают и как
  проверяющий эксперт может проверить их получение.

Способ хранения и просмотра логов вы выбираете самостоятельно.

### 6. Поддержка операционной системы

Необходимо подтвердить работоспособность решения на следующей операционной
системе:

- Ubuntu 24.04.

Данная операционная система свободно доступна для скачивания и не
ограничена к использованию.

### 7. Автоматизация развертывания

Решение должно быть воспроизводимым.

После выполнения описанной вами последовательности действий проверяющий
эксперт должен иметь возможность получить работоспособное решение без
ручного создания и редактирования Kubernetes-ресурсов.

Повторный запуск процесса развертывания не должен приводить систему в
некорректное состояние.

Разрешается использовать:

- Kubernetes manifests;
- Helm;
- Kustomize;
- Terraform;
- Ansible;
- shell-скрипты;
- Python-скрипты;
- иные open-source инструменты.

Ручная настройка каждого Kubernetes-ресурса через графический интерфейс
не считается полноценной автоматизацией.

Желательно свести развертывание к минимальному количеству понятных команд.

### 8. Документация

В Git-репозитории должна находиться инструкция, позволяющая понять
архитектуру решения, развернуть его и проверить работоспособность основных
компонентов.

## Что необходимо сдать

Решением онлайн-этапа является ZIP- или RAR-архив, содержащий два
обязательных артефакта:

1. **TXT-файл со ссылкой на Git-репозиторий.** В репозитории должно

2. **Паспорт решения.** Краткий документ, который позволит проверяющим

Подробные требования к каждому артефакту — в разделе
«Требования к сдаче решения».

Отсутствие обязательной части решения может стать основанием для
недопуска работы к полной экспертной оценке.

**Условия прохода в финал.** В очный финал (Москва) приглашаются топ-10
участников по итогам онлайн-этапа. Отбор осуществляется по оценке жюри на
основе критериев № 1–5.

## Требования к сдаче решения

### Общие требования

Решение сдаётся в виде архива, содержащего:

- TXT-файл со ссылкой на Git-репозиторий;
- паспорт проекта.

Технические требования к архиву:

| Параметр | Требование |
|---|---|
| Формат | ZIP или RAR |
| Объем | не более 18 МБ |
| Название архива | фамилия участника (как указывали при регистрации) |
| Файлы внутри | `Ссылка.txt` и `Паспорт.doc` / `Паспорт.pdf` |

Приём решений производится **до 4 октября 23:59**, решения просят
присылать заблаговременно.

Чтобы сдать решение, нажмите кнопку «Загрузить» на той же странице, на
которой скачали задание, и прикрепите архив. Чтобы заменить уже сданное
решение, нажмите «Загрузить другой файл» рядом с плашкой «Решение
загружено» — новый архив заменит предыдущий.

### Требования к Git-репозиторию

**Технические требования:**

- репозиторий может быть размещен на GitHub, GitLab или другом публично
  доступном Git-хостинге;
- решение должно располагаться в основной ветке `main`;
- репозиторий должен оставаться публично доступным до публикации списка
  финалистов.

> **ВАЖНО:** Git-репозиторий должен быть публичным и доступным без
> авторизации на протяжении всего периода проверки. Эксперты должны иметь
> возможность клонировать репозиторий стандартными средствами Git. Перед
> сдачей убедитесь, что `git clone <URL>` выполняется без запроса
> дополнительных прав доступа.
>
> Внесение изменений в ветку репозитория после **4 октября 23:59**
> **категорически запрещено** и может привести к дисквалификации.

**В репозитории должны находиться:**

1. **Исходные файлы для развертывания** — все Kubernetes manifests, Helm
   charts, Kustomize-конфигурации, Terraform/Ansible-файлы, скрипты и
   другие материалы, необходимые для воспроизведения решения.
2. **Конфигурация Gateway API** — все файлы для развертывания и настройки
   Gateway API.
3. **Конфигурация мониторинга** — материалы для настройки Prometheus и
   сбора заявленных метрик.
4. **Конфигурация логирования** — конфигурация Fluentd или Filebeat и иных
   компонентов выбранной схемы работы с логами.
5. **README.md** — должен позволить эксперту понять и воспроизвести
   решение.

README обязательно должен содержать:

- краткое описание решения;
- архитектуру;
- список использованных технологий и их версий;
- использованную версию Kubernetes;
- выбранную реализацию Gateway API;
- требования к среде;
- пошаговую инструкцию по развертыванию;
- команду или последовательность команд для запуска;
- инструкцию по проверке доступности приложения;
- инструкцию по проверке мониторинга;
- инструкцию по проверке логирования;
- описание дополнительных возможностей;
- известные ограничения решения.

**Желательно** свести первоначальное развертывание к одной или нескольким
явно описанным командам, например:

```bash
make deploy
```

или

```bash
./deploy.sh
```

или аналогичному сценарию.

### Требования к безопасности

Не размещайте в репозитории:

- реальные пароли;
- API-токены;
- приватные SSH-ключи;
- персональные данные;
- другие секреты.

Если для работы решения необходимы секреты, предусмотрите безопасный способ
их передачи через переменные окружения, Secret или шаблон конфигурации.

### Формат сдачи ссылки

В архив приложите TXT-файл, который содержит **только** ссылку на
актуальную ветку Git-репозитория. Файл должен называться `Ссылка.txt`.

### Требования к паспорту проекта

Паспорт решения используется экспертами для скрининга работ. Его задача —
позволить за несколько минут понять:

- что было реализовано;
- как устроено решение;
- какие обязательные компоненты работают;
- какие дополнительные возможности реализованы;
- стоит ли направлять решение на углубленную техническую проверку.

**Формат:**

| Параметр | Требование |
|---|---|
| Тип файла | PDF или DOC/DOCX |
| Объем | не более 4 страниц |
| Размер файла | не более 15 МБ |

Не рекомендуется превращать паспорт в полноценную презентацию или
техническую документацию. Подробная документация должна находиться в
Git-репозитории.

**Структура:**

#### Страница 1. Архитектура и состав решения

Укажите:

- используемую версию Kubernetes;
- способ развертывания Kubernetes;
- выбранную реализацию Gateway API;
- используемые инструменты автоматизации;
- используемый инструмент логирования — Fluentd или Filebeat;
- способ развертывания Prometheus;
- операционную систему, на которой тестировалось решение.

Добавьте простую архитектурную схему. На схеме рекомендуется показать

#### Страница 2. Реализованный функционал

Для каждого **обязательного** пункта решения:

- как технически был реализован;
- обоснование выбора / реализации;
- как проверяющий эксперт может проверить работоспособность.

Для каждого **дополнительного** улучшения решения:

- что было реализовано;
- как технически было реализовано;
- обоснование выбора / реализации;
- как проверяющий эксперт может проверить работоспособность.

#### Страница 3. Ревью работы и потенциальное масштабирование

Кратко (не более 3 предложений на пункт) укажите:

- **Главная особенность решения** — что вы считаете наиболее сильной
  технической стороной проекта.
- **Самое сложное принятое решение** — между какими вариантами выбирали и
  на основании чего приняли решение.
- **Предложения по дальнейшему развитию** — списком: что можно добавить в
  решение и что для этого необходимо (например, платные сервисы или
  специфическая инфраструктура). При возможности рекомендуется учитывать
  телеком-специфику.

> **Важно.** Паспорт решения не заменяет репозиторий. Все заявленные в
> паспорте возможности должны подтверждаться содержимым Git-репозитория и
> могут быть проверены экспертами. Если заявленная функциональность
> отсутствует в репозитории или не может быть воспроизведена, она не
> учитывается при выставлении итоговой оценки.
