## Цель

Подтвердить, что эксперт, действуя буквально по корневому `README.md` на
чистой Ubuntu 24.04, получает работающее решение. Зафиксировать время
установки и потребление ресурсов, собрать скриншоты для паспорта.

## Scope

### Входит

- откат VM на снимок `clean-ubuntu-v2` (чистая Ubuntu 24.04.5);
- `git clone` публичного репозитория без авторизации, далее — только
  команды из README: `sudo ./deploy.sh`, повторный запуск, `make verify`,
  `make demo`, ручные проверки из раздела 6, доступ через браузер по
  разделу 7;
- замеры: время первой установки и повторного запуска, RAM, диск, число
  подов;
- скриншоты: дашборды Grafana, Argo CD, вывод `make verify`;
- исправление найденного в коде и в README.

### Не входит

- паспорт (PASSPORT-001), сборка архива (SUBMIT-001).

## Технические требования

- Команды выполняются в том порядке и в том виде, в каком они записаны в
  README; расхождение вывода с описанным — дефект README или кода.
- Исправления кода проходят тот же цикл: lint → `deploy.sh` дважды →
  `verify.sh` → зелёный CI.

**Найдено и исправлено (`scripts/release.sh`, функция `reset`):**
- **`make verify` сразу после `make demo` или `make release-reset` находил
  демо-версию.** `kubectl argo rollouts status` возвращал `Healthy` ещё для
  прежней ревизии, и около минуты после возврата трафик обслуживали поды
  v1.1 (`Hello World! v1.1 …` вместо ожидаемого ответа). Состояние затем
  приходило в норму само. Теперь `reset` ждёт, пока контроллер обработает
  изменение (`observedGeneration`), стабильной станет текущая ревизия и не
  останется подов прежних ревизий.
- **Релиз, запущенный сразу после `make release-reset`, откатывался.**
  `reset` запускал синхронизацию Argo CD и не ждал её завершения, если
  приложение уже было `Synced`; ещё идущая синхронизация возвращала шаблон
  из Git поверх только что начатого релиза. Теперь `reset` ждёт завершения
  операции (снятия поля `.operation`).

Проверено на стенде итоговой версией скрипта, каждый раз `make verify`
запускался без паузы:

| Последовательность | Результат |
|---|---|
| `release-good` → `release-reset` → `verify` | возврат 39 с; 46 из 46 |
| `make demo` (полный) → `verify` | демо 237 с, код 0; 46 из 46 |
| `release-reset` (без изменений, 3 с) → `release-bad` → `release-reset` → `verify` | плохой релиз откатан автоматически; 46 из 46 |
| `release.sh good && release.sh reset` → `verify` → `make demo --auto --no-release` | 178 с; 46 из 46; код 0 |

В CI обе гонки не проявлялись: между шагами релизов есть ожидание чистого
окна анализа, а `verify` выполняется до релизов.
