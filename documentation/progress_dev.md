## Статусы

| Статус | Смысл |
|---|---|
| `planned` | Задача известна, но ещё не разрешена к старту |
| `ready` | Постановка готова, все обязательные зависимости закрыты |
| `in_progress` | Работа выполняется |
| `blocked` | Есть конкретная незакрытая зависимость |
| `done` | Результат реализован и проверен |
| `cancelled` | Задача отменена с сохранением причины |

## Параллельность

- Основная линия: DOCS-001 → CLUSTER-001 → APP-001 → GW-001 → AUTO-001 →
  QA-001.
- MON-001 зависит только от кластера, её можно брать параллельно с APP-001 и
  GW-001.
- LOG-001 зависит только от APP-001 и может идти параллельно с GW-001.
- Автоматизация пишется с первой задачи, а не в конце: каждая задача
  оставляет свой шаг в скриптах. AUTO-001 сводит их в одну команду и
  проверяет идемпотентность.
- Дополнительные возможности берутся только после QA-001: кейс не засчитывает
  дополнительную функциональность без работающей базы. Исключение — CI-001:
  его e2e-job и есть автоматическая проверка базы.
- Черновик паспорта можно вести параллельно с реализацией, но финализировать
  после DOCS-002.

## Definition of Ready

Задача переводится в `ready`, если:

1. определён наблюдаемый результат и границы scope;
2. указаны связанные разделы architecture.md и пункты кейса;
3. закрыты обязательные зависимости;
4. критерии приёмки и команды проверки воспроизводимы;
5. все решения D-NN, от которых задача зависит, приняты.

## Definition of Done

Задача переводится в `done`, если:

1. все критерии приёмки подтверждены реальным запуском, а не «должно
   работать»;
2. изменения в кластере сделаны кодом из репозитория, без ручных правок;
3. повторный запуск шага проверен и не ломает состояние;
4. версии всех добавленных компонентов зафиксированы;
5. в репозитории нет секретов;
6. заполнен «Результат закрытия», статус обновлён здесь и в task-файле.
