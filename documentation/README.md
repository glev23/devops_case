# Документация проекта

Решение кейса онлайн-этапа DevOps-хакатона. Нужно с нуля развернуть в
Kubernetes простое веб-приложение, открыть к нему доступ через Gateway API,
собирать метрики в Prometheus, а логи приложения — через Fluentd или Filebeat.
Всё должно воспроизводиться на Ubuntu 24.04 по инструкции из репозитория.

**Срез 2026-09-30:** кейс переведён в Markdown, заведена стартовая
документация (DOCS-001, `in_progress`). Следующий шаг — выбрать стек по
открытым решениям в [architecture.md](./architecture.md#открытые-решения),
после этого [CLUSTER-001](./progress_dev.md) получит статус `ready`.

## Как устроена документация

- **Технические решения** принимаются в `architecture.md`. Пока решение не
  принято, оно лежит в разделе «Открытые решения» с кандидатами. После выбора
  переносится в соответствующий раздел с обоснованием.
- **Ничего не удаляется молча.** Изменённое решение фиксируется в разделе
  «История решений»: дата, что изменилось и почему. Из этой истории потом
  собирается страница 3 паспорта («самое сложное решение»).
- **Факты отделены от предположений.** Версия компонента, флаг или
  совместимость считаются фактом только после сверки с официальной
  документацией или реального запуска. Непроверенное помечается явно.
- **Всё, что заявлено, проверяемо.** У каждой возможности, которая попадёт в
  README или паспорт, есть команда проверки с ожидаемым результатом. Кейс
  прямо говорит: невоспроизводимое не засчитывается.
- **Секреты не попадают в репозиторий.** Только шаблоны (`*.example`),
  переменные окружения и Kubernetes Secret, создаваемый при развёртывании.

## Как продолжить работу

1. Открыть [progress_dev.md](./progress_dev.md).
2. Взять первую задачу `ready` с закрытыми зависимостями. Если task-файла
   ещё нет, завести его по шаблону из [tasks/README.md](./tasks/README.md).
3. Если задач `ready` нет, не начинать `blocked` или `planned` без явного
   запроса.
4. Выполнять только то, что входит в задачу. Всё, что найдено за её
   пределами, оформляется новой строкой в очереди, а не расширением текущей
   задачи.
5. Пройти проверки из task-файла. Каждая задача, которая меняет кластер,
   оставляет после себя автоматизацию: ручной `kubectl apply` в финальную
   инструкцию не попадает.
6. Заполнить «Результат закрытия», обновить статус в task-файле и
   `progress_dev.md`. Остальные документы менять только если изменились
   факты, решения, команды или адреса.

Команды развёртывания здесь намеренно не дублируются. Их единственный
источник — корневой `README.md` репозитория (DOCS-002).
